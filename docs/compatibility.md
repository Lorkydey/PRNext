La compatibilité npm ne garantit pas la compatibilité des paquets qui dépendent des internes de Next.js. Les bibliothèques qui demandent un vrai socket HTTP, un `http.ServerResponse` natif, des upgrades ou des fonctionnalités serveur non exposées doivent être adaptées. L'adresse réseau réelle du client n'est pas transmise au faux socket Node utilisé pour le contexte de requête.

Les Server Actions restent limitées à l'App Router. Les modules `'use server'` acceptent les réexports `export *` ESM analysables au build, y compris les cycles et alias ; les exports ambigus sont exclus selon les règles ESM et les valeurs non async sont refusées. Les actions définies comme méthodes d'objet ou de classe restent refusées. Les captures inline acceptent les valeurs sérialisables usuelles, les cycles et les références à d'autres Server Actions ; les instances de classes applicatives et les fonctions ordinaires capturées sont refusées. Les redirections d'action utilisent `push` par défaut, et `notFound()` rend le fallback 404 avec les cookies déjà modifiés. L'option `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` accepte une clé AES de 16, 24 ou 32 octets encodée en base64 au build ; les identifiants d'action restent renouvelés à chaque build, même avec une clé fixe.

Dans l'App Router, les addons absents au build et téléchargés seulement à l'exécution ne peuvent pas être détectés par cette inspection. Un fichier `.node` importé directement depuis les sources locales doit être emballé dans un package npm. Les packages mêlant leur propre chargeur natif calculé à du CSS ou des frontières client nécessitent encore du travail ; ils restent compilés pour préserver ces transformations. Les exports conditionnels navigateur des dépendances natives restent utilisables lorsqu'ils sélectionnent une implémentation compatible navigateur.

Les modules applicatifs restent en mémoire dans chaque worker, comme dans un serveur Node ordinaire. Les états globaux des packages sont donc persistants par worker. Le worker ne constitue pas un bac à sable pour du code non fiable.

Le [cache de données](caching.md) réside dans `.rustyx-cache/`, hors du dossier de build. Les appels au build Pages et App statiques exécutent leur producteur sans cache persistant, faute de serveur natif actif. Les appels `unstable_cache` imbriqués et les routes `force-no-store` exécutent directement leur producteur sans remplir une entrée indépendante : Next peut encore écrire ces résultats lors de certains contournements de lecture. Les limites de stockage entraînent des évictions ; une durée infinie ne garantit donc pas la conservation d'une valeur.

Chaque flux dynamique occupe un worker jusqu'à sa fin. Un client déconnecté entraîne l'arrêt du processus concerné ; le serveur libère ses tampons et sa capacité, mais ne garantit pas l'exécution des callbacks applicatifs d'annulation avant cet arrêt. Les API progressives ont un délai d'inactivité de 25 secondes ; le transport natif coupe aussi un producteur ou consommateur bloqué après 30 secondes. Les rendus App conservent leurs délais de rendu, même si leur réponse a commencé. Les erreurs après envoi des en-têtes ne peuvent plus devenir une nouvelle réponse HTTP 500/504.

Références utilisées pour définir les contrats : [routage Pages](https://nextjs.org/docs/pages/building-your-application/routing), [`getServerSideProps`](https://nextjs.org/docs/pages/building-your-application/data-fetching/get-server-side-props), [Server et Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components), [layouts](https://nextjs.org/docs/app/api-reference/file-conventions/layout), [NextResponse](https://nextjs.org/docs/app/api-reference/functions/next-response), [API esbuild](https://esbuild.github.io/api/).

Quelques imports internes de Next disposent désormais d’adaptateurs explicites : `next/dist/shared/lib/router-context.shared-runtime` (et l’ancien chemin `router-context`) expose le véritable `RouterContext` Pages ; `next/dist/shared/lib/app-router-context.shared-runtime` expose `AppRouterContext` avec les méthodes de navigation App. Les providers SSR, navigateur et Edge partagent les contextes appropriés. Les autres exports de ce module privé, les arbres internes de layouts, les manifestes et les hooks privés de plugins Next ne sont pas reproduits. Ce support ciblé ne rend pas les internes arbitraires de Next compatibles.
