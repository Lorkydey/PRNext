# Internationalisation Pages

La configuration `i18n` accepte `locales`, `defaultLocale`, `localeDetection` et `domains` (`domain`, `defaultLocale`, `locales`, `http`). Jusqu'à 100 langues sont autorisées. Hors domaine localisé, Rust choisit la langue à la racine via `NEXT_LOCALE`, puis `Accept-Language`. Sur un domaine configuré, la langue par défaut du domaine s’applique et `Accept-Language` peut déclencher une redirection vers un autre domaine configuré. Les pages partagent leurs bundles JS et CSS ; leurs HTML, données JSON et entrées ISR sont distincts par langue.

`getStaticProps`, `getServerSideProps` et les contextes Pages reçoivent les informations de langue. `getStaticPaths({locales, defaultLocale})` accepte les chemins préfixés ou `{params, locale}` et conserve les comportements `fallback`. `router.locale`, `router.locales`, `router.defaultLocale`, `Link locale`, les options `locale` des navigations et `locale: false` sont pris en charge. Les chemins `router.pathname` et `router.asPath` restent logiques, sans préfixe de langue. Les pages d'erreur statiques sont également localisées.

Les règles personnalisées et matchers middleware sont étendus aux langues, sauf `locale: false`. `NextRequest.nextUrl` expose la langue et le domaine et conserve ces informations dans ses setters et ses clones. L'App Router conserve ses conventions explicites de segments de langue ; la configuration Pages n'ajoute pas automatiquement des routes App localisées. `output: 'export'` ne se combine pas avec cette configuration.

Les tests couvrent la navigation avec état partagé, le SSR, SSG, JSON, les chemins bloquants, les erreurs, les domaines, les réécritures et le middleware. Les combinaisons de domaines, middleware et règles applicatives restent à vérifier sur le projet importé : ces tests ne certifient pas une équivalence universelle avec Next.
