# Compilation, hooks et loaders

PRNext utilise esbuild par défaut. Lorsqu'un callback webpack configure des loaders ou qu'un plugin exige le graphe webpack, un backend webpack réel prend en charge les modules, les chunks et les assets de la cible concernée. Le serveur HTTP, le routage, les images et les caches persistants restent natifs Rust ; webpack s'exécute seulement pendant la compilation.

`next.config.*` peut déclarer `webpack(config, context)`. PRNext fournit `dev`, `buildId`, `isServer`, `nextRuntime`, le package webpack et `defaultLoaders.babel`. Le callback est évalué séparément pour les cibles navigateur, Node et Edge utilisées. Les alias et extensions de résolution, `module.rules` et les expressions littérales simples de `DefinePlugin` sont raccordés au compilateur. Les objets imbriqués, regex, définitions `typeof` et valeurs `runtimeValue` utilisent le vrai DefinePlugin dans webpack. Les alias webpack acceptent une correspondance exacte suffixée par `$`, `false` pour un module vide et des tableaux de destinations de repli. Comme webpack, une destination relative se résout depuis l'importeur ; utiliser un chemin absolu calculé depuis `config.context` pour viser la racine du projet. Les alias Turbopack sont relatifs à `turbopack.root`, ou à la racine du projet si cette option est absente. `EnvironmentPlugin` accepte les valeurs d'environnement et les valeurs par défaut ; une variable absente sans défaut provoque une erreur. `BannerPlugin` accepte une chaîne statique, `raw` et `footer`, injectés avant le calcul des noms de bundles. Les bannières calculées et les filtres par chunk déclenchent le backend webpack. `defaultLoaders.babel` délègue la syntaxe à esbuild ; pour une transformation Babel personnalisée, fournir `babel-loader`.

Les plugins non traduits vers esbuild reçoivent un véritable `Compiler`, `NormalModuleFactory`, `Compilation`, `moduleGraph` et `chunkGraph`. Ils peuvent remplacer une dépendance (`NormalModuleReplacementPlugin`), injecter des imports (`ProvidePlugin`), ignorer une dépendance (`IgnorePlugin`, avec son comportement webpack de module absent), inspecter les modules, optimiser les chunks et modifier les bundles via `processAssets`. Les hooks synchrones et asynchrones suivent le cycle webpack. Les noms contenant un hash de contenu sont produits par webpack après ces transformations.

Le backend raccorde la résolution et les transformations PRNext avant l'analyse des modules : séparation serveur/client, Server Actions, Cache Components, Edge, CSS Modules, images et imports du framework. Les bibliothèques React côté serveur restent externes pour partager les mêmes instances. Le chargement Flight du navigateur utilise explicitement l'adaptateur PRNext, distinct du runtime webpack des chunks. Les imports d'URL calculées du runtime conservent leur exécution native dans le navigateur.

La publication reste atomique : une erreur de plugin conserve le dernier build valide. Les chemins d'assets sortant du répertoire et les collisions de contenus sont refusés. Chaque compilateur est fermé après son travail ; ses registres et fichiers temporaires sont libérés. Chaque build reçoit une identité de runtime webpack distincte, pour éviter de réutiliser un ancien module après le changement d'un chunk synchrone. Les instances React de développement restent partagées pour Fast Refresh. Le backend ajoute un coût de compilation aux cibles qui l'utilisent. La minification utilise esbuild séquentiellement, sans pool de workers Terser supplémentaire, et partage le cache borné des transformations.

Chaque graphe RSC, SSR, navigateur ou Edge reste compilé séparément. Les plugins qui supposent les noms de compilateurs, les manifestes ou les hooks privés propres à Next, ou un unique graphe global Next, ne sont pas garantis compatibles. Les options de `next.config.webpack` acceptées restent celles décrites ici : ce backend ne reproduit pas toutes les options de configuration Next. Sur Edge, aucun chunk ne doit nécessiter un chargeur Node : la sortie est regroupée pour son exécution dans la VM.

Les règles prennent en charge `test`, `include`, `exclude`, `issuer`, `resourceQuery`, `oneOf`, `rules`, `use`, `loader`, `options` et `enforce`. Les loaders sont résolus dans le projet. Le runner officiel exécute leur ordre normal et leur phase `pitch`, leurs callbacks asynchrones et leurs entrées binaires. `getOptions` valide les schémas ; `addDependency`, `addContextDependency`, `addMissingDependency`, `cacheable`, `resolve`, `getResolve()`, les diagnostics et `emitFile` sont raccordés. Les fichiers émis sont servis sous le préfixe d'assets du projet. Les règles s'appliquent aux modules importés. Les conventions de page `.mdx` nécessitent encore un raccordement des loaders avant le scan des routes ; ce support ne suffit pas à reproduire le plugin Next MDX complet. Le résultat doit être du JavaScript ; il repasse par les transformations PRNext des composants client, des actions, des caches et de Fast Refresh. Les actions ne passent donc pas dans un bundle navigateur à travers un loader.

Sans callback webpack, `turbopack.rules` accepte des motifs glob avec `{ loaders: [...], as: '*.js' }` ou `as: '*.jsx'`. En présence des deux configurations, les règles webpack ont priorité. Une règle peut aussi être un tableau de variantes. `condition` accepte `all`, `any`, `not`, les tests `path` (glob ou regex) et `content` (regex), ainsi que `browser`, `node`, `edge-light`, `development`, `production` et `foreign`. Une expression est limitée à 256 nœuds et 32 niveaux ; le contenu n'est lu que lorsqu'un test `content` est atteint. Les regex réutilisées sont réinitialisées entre fichiers. `foreign` couvre les dépendances dans `node_modules` et les fichiers internes PRNext ; les packages de workspace hors de ces répertoires restent applicatifs. Voir le [contrat des conditions Turbopack](https://nextjs.org/docs/app/api-reference/config/next-config-js/turbopack#advanced-webpack-loader-conditions).

Avec une configuration webpack contenant des règles, `importModule` et `loadModule` utilisent le véritable exécuteur de modules webpack ; `getResolve(options)` accepte les options de son résolveur. Les formes callback et Promise suivent le [contrat webpack](https://webpack.js.org/api/loaders/). Ces appels désactivent la persistance du résultat du loader : leurs dépendances sont suivies par webpack et ne doivent pas être remplacées par une empreinte disque incomplète. Les loaders simples conservent le cache disque borné. Les requêtes inline et leurs préfixes `!`, `-!`, `!!` fonctionnent dans les graphes webpack, avec l'ordre pre/normal/inline/post et des identités distinctes pour chaque chaîne. Les transformations de sécurité des frontières React restent appliquées même avec `!!`. Les graphes esbuild sans configuration webpack ne prennent pas en charge ces helpers avancés ni les imports inline. Les cartes fournies par les loaders sont conservées dans leur cache et composées avec les transformations JS/TSX de PRNext, esbuild, webpack et sa minification. La suppression des exports serveur Pages, `next/dynamic`, les actions, Cache Components et les polices composent leurs cartes Babel ; Fast Refresh corrige aussi le décalage de son préambule. La réécriture des imports de chunks Node actualise la carte externe. Les factories Edge préservent leurs coordonnées. Une transformation tierce qui supprime sa carte reste une rupture de traçabilité ; la totalité des chemins CSS/PostCSS/Sass n’est pas couverte par cette validation JS/TSX. Ce support ne constitue pas une implémentation complète de webpack ou de Turbopack.

## Configurations de plugins Contentlayer

La règle `type: 'javascript/auto'` avec `resolve: { fullySpecified: false }`, ajoutée par `next-contentlayer2`, est acceptée : elle correspond au traitement JS/ESM déjà appliqué par le backend. Les autres types et réglages de résolution par règle restent refusés. `webpack.watchOptions.ignored` accepte une chaîne, une regex ou un tableau de chaînes et est transmis au compilateur webpack pour ses plugins ; les autres options de surveillance restent refusées. PRNext utilise son propre watcher de sources et exécute webpack avec `run`, sans démarrer un second watcher webpack.

`turbopack.root`, lorsqu'il est fourni, doit être absolu. Les alias relatifs et motifs/conditions de loaders Turbopack utilisent cette base. Le dossier contenant `app/` et `pages/` reste celui passé au CLI, ainsi que la portée du watcher PRNext ; ce réglage ne reproduit pas l'isolation du système de fichiers ni la surveillance étendue de Turbopack. Sans `root`, la base reste le dossier de l'application.

Le CLI `build`/`dev` fixe le répertoire de travail et `INIT_CWD`/`PWD` au dossier de l'application pour les plugins qui les lisent. `onDemandEntries` est validé pour charger ces wrappers, avec la différence de politique mémoire décrite dans le [guide de configuration](configuration.md). Les plugins de génération continuent à exécuter leurs véritables hooks `beforeCompile` ; PRNext ne remplace pas Contentlayer par des données préfabriquées.

Le pont webpack préserve les URL CSS externes et les conditions des `@import`. Les polices et images locales référencées par `url()` sont émises comme ressources binaires ; elles ne deviennent pas des imports JavaScript. Voir la [validation du blog Contentlayer](contentlayer.md) pour les essais sur un projet réel et les problèmes applicatifs encore observés.

## Incrémentalité et mémoire

En développement, un processus de compilation persiste entre les modifications. Les contextes esbuild conservent leurs graphes et leurs caches de parsing ; les plugins PRNext sont réinitialisés avec les données du nouveau build. Les entrées et sorties utilisent une identité stable dans le compilateur, tandis que la publication conserve les répertoires temporaires et le remplacement atomique. Une erreur laisse la dernière application valide disponible.

Au plus huit contextes esbuild de graphes applicatifs et deux contextes auxiliaires sans plugins sont conservés. Les auxiliaires disposent de leur propre budget d'éviction et ne chassent pas les graphes applicatifs. Le processus est recyclé après 24 builds ou lorsque son RSS dépasse 512 Mio à la fin d'un build, ainsi qu'après une erreur ou une modification de la configuration ou des dépendances déclarées. Ce seuil de recyclage n'est pas un plafond de consommation pendant une compilation.

Les résultats des loaders qui autorisent le cache sont conservés dans `.prnext-cache/loaders-v1`. Leur source, leurs options, la cible, l'environnement, les fichiers dépendants, les répertoires surveillés et les dépendances absentes participent à la validation. Les assets sont réémis depuis le cache. Le stockage est limité à 256 entrées et 64 Mio, avec 16 Mio maximum par entrée. Un loader doit déclarer ses lectures externes ou utiliser `cacheable(false)` ; les effets externes et dépendances réseau ne peuvent pas être déduits automatiquement.

L'analyse des configurations de segments App conserve au plus 256 résultats, avec 1 Mio de chemins et résultats sérialisés et 64 Kio maximum par entrée, hors métadonnées du moteur. Le contenu source est relu et haché : un changement conservant la taille et la date du fichier invalide correctement l'entrée. Aucun AST n'est conservé.

La suppression du code serveur Pages, `next/dynamic`, Fast Refresh, Cache Components, la validation Edge, la réécriture des imports de chunks et les transformations/minifications du backend webpack réutilisent leurs résultats dans un cache commun borné à 256 entrées et 2 Mio de chaînes UTF-16 comptabilisées, avec 128 Kio maximum par entrée, hors métadonnées du moteur. Source, fichier, cible, options et racine du projet participent à l'identité selon la transformation. Les transformations Cache Components incluent aussi l'identité du build et les gestionnaires ; les erreurs ne sont pas mises en cache. Ces caches vivent dans le processus de compilation, pas dans le serveur de production.

La précompression gzip réutilise les contenus identiques entre builds via `.prnext-cache/precompress-v1`, limité à 512 entrées et 64 Mio sur disque, avec 4 Mio maximum par sortie stockée. Deux pipelines à buffers bornés vérifient le contenu décompressé et son empreinte avant réutilisation ; une entrée corrompue est recalculée. Les fichiers source de plus de 64 Mio sont compressés sans être mis en cache. Les dates des sorties restent synchronisées avec les sources pour les contrôles du serveur Rust.

Les noms et types des entrées de répertoires sont réutilisés après vérification de leur identité, taille, mtime et ctime nanoseconde. Ce cache conserve au plus 256 répertoires et 1 Mio de chaînes comptabilisées, avec 64 Kio par entrée. Les ajouts, suppressions et renommages invalident la liste ; les contenus des sources restent relus et hachés. L’analyse des Server Actions réutilise des gabarits sérialisés dans le cache commun de transformations, tout en renouvelant les identifiants HMAC et les clés de chiffrement à chaque build. Aucun AST supplémentaire n’est conservé.

Le parcours de ces métadonnées, certaines transformations de framework, les étapes de liaison et les rendus de validation restent effectués lors d'une reconstruction. Le compilateur webpack et ses plugins restent recréés pour ne pas conserver leurs captures de configuration ou ignorer leurs effets de build. Les rendus susceptibles de dépendre du réseau, de l'heure ou d'effets applicatifs ne sont pas réutilisés sur la seule base des sources. Il ne s'agit donc pas encore d'une compilation entièrement incrémentale comparable à tous les chemins de Turbopack.

## Vérifications

Les tests du backend exécutent des remplacements de dépendances, ProvidePlugin, IgnorePlugin, des bannières calculées, des loaders injectés via les hooks du graphe, des hooks sur les vrais modules/chunks et des modifications de bundles. Un test navigateur couvre CSS Modules, imports différés, navigation des deux routeurs sans rechargement, Edge et Server Actions avec ces plugins actifs. Deux tests supplémentaires modifient un composant pendant une session webpack et vérifient Fast Refresh avec conservation d'état sur Pages et App. Les tests des caches vérifient les changements de source, de cible et d'identité du build, les échecs récupérables et les bornes communes de mémoire.

La comparaison optionnelle `npm run test:next-compat` (avec `PRNEXT_NEXT_REFERENCE` pointant vers Next 16.3.5) couvre aussi `importModule`, les alias exacts/désactivés/à destinations multiples, les définitions imbriquées et `next/compat/router`. Ces cas ciblés ne constituent pas une certification de compatibilité exhaustive.

Les callbacks du service esbuild réentrent explicitement dans le contexte de leur build : une compilation ultérieure ne peut pas hériter du mode sourcemaps, du registre d’actions ou de la configuration du premier projet traité par le service. Les tests vérifient aussi les coordonnées d’erreurs après plusieurs transformations, le cache des loaders et la séparation des contextes de compilation.
