# Cache Components

Les artefacts PPR immuables peuvent maintenant être enregistrés une seule fois entre threads et référencés par un identifiant borné. Les modèles dont les trous remplacent des champs entiers à la racine disposent aussi d’une continuation directe ; les cas imbriqués conservent le chemin Flight complet. Voir les [conditions et limites](resource-optimization.md).

La reprise PPR évite désormais les promesses inutiles pour les valeurs Flight statiques déjà résolues et mémorise les accès aux parents du modèle vivant pendant une seule requête. Les modules de route de production utilisent un registre de 64 entrées maximum. Après chaque lecture validée du cache natif, un mémo du JSON d’artefact peut réutiliser son objet si les octets sont strictement identiques : 16 entrées, 64 Kio par entrée, 256 Kio de JSON encodé au total, alloués à la demande. Les objets JavaScript décodés et les réponses en cours s’ajoutent à ce budget ; il ne s’agit pas d’une limite RSS. Le mémo ne supprime ni la lecture native ni le contrôle d’invalidation. La continuation opaque React est clonée pour chaque reprise HTML, car React peut la modifier ; les modèles vivants, cookies et contextes restent propres à la requête.

Le thread RSC de production peut également préparer une représentation statique réutilisable, en supprimant les objets internes du décodeur React. Le registre est limité à 8 entrées et à un budget comptable de 512 Kio (deux octets par caractère Flight et 128 octets par nœud), avec au plus 64 Kio de Flight base64 par entrée. Ce budget est une règle de rétention, pas une mesure exacte du heap. La clé compare le contenu Flight et les identités des manifestes client et actions. Chaque reprise reconstruit son modèle vivant séparément. Les promesses et les trous distincts conservent leur identité ; les flux, fonctions serveur, vues binaires et structures non rejouables utilisent le décodeur ordinaire. Une invalidation reste contrôlée en amont par le cache natif. Aucun objet du décodeur contenant une réponse ou un contexte de requête n’est stocké dans ce registre.


Le chemin PPR regroupe maintenant la résolution de la génération, la lecture de l'entrée et l'acquisition éventuelle de son lease dans une transaction Rust et un seul échange. Un remplissage vérifie toujours la génération avant de réutiliser l'artefact du build ; une invalidation rend les anciennes écritures inapplicables. En cas d'indisponibilité du cache, l'enveloppe est recalculée. Les requêtes SQLite sont préparées une fois puis réutilisées, avec un plafond de 32 statements par connexion et libération de leurs paramètres après utilisation. Les limites du cache de données restent inchangées. Le décodeur SSR réutilise aussi les correspondances de modules via des références faibles, en vérifiant leurs chemins et leur répertoire de build à chaque appel. Aucun arbre React décodé ni contexte de visiteur n'y est conservé.

Les échanges avec le cache Rust local utilisent un pool HTTP persistant borné pour réduire le coût des lectures répétées en PPR. Chaque lecture continue à vérifier le protocole natif de fraîcheur et d'invalidation ; les générations ne sont pas mémorisées côté JavaScript. Le pool évite de conserver les contextes des requêtes terminées. En production, le worker RSC utilise une jeune génération V8 de 16 Mio pour limiter les allocations temporaires résidentes, sans modifier la limite de l'ancienne génération. Voir le [rapport d'optimisation](../reports/next-migration-optimized/optimization.md) pour les gains mesurés et leurs limites.

Activer `cacheComponents: true` dans `next.config.*` ou `prnext.config.*` permet les directives `'use cache'`, `'use cache: remote'` et `'use cache: private'` dans les fonctions serveur async et les modules de fonctions async exportées.

```tsx
import { cacheLife, cacheTag } from 'next/cache'

export async function Products({ category }) {
  'use cache'
  cacheLife('hours')
  cacheTag('products', `category:${category}`)
  return <ProductList category={category} />
}
```

Le compilateur construit une identité propre au build et inclut les arguments et variables capturées dans la clé. Les composants utilisent le sérialiseur Flight officiel : JSX, références aux composants client, données structurées et enfants opaques restent compatibles avec l'hydratation. Un enfant opaque passé par l'appelant n'entre pas dans le résultat partagé sous forme de données privées ; il est réinjecté à la lecture. `searchParams` n'est pas lisible directement dans une page mise en cache : lire la valeur hors de la portée et la passer comme argument.

`cacheLife` accepte `default`, `seconds`, `minutes`, `hours`, `days`, `weeks`, `max`, des profils `cacheLife` définis dans la configuration ou un objet `{ stale, revalidate, expire }`. Les appels imbriqués propagent tags et durées minimales, sauf lorsqu'une durée est explicitement choisie par le parent. `cacheTag`, `revalidateTag`, `updateTag` et `revalidatePath` partagent le cache natif. Les tags découverts après le rendu sont enregistrés lors de la publication ; une invalidation concurrente empêche la publication d'une ancienne valeur.

Les caches publics résident dans SQLite et survivent aux redémarrages. Les baux évitent les calculs concurrents d'une même entrée ; les lectures périmées peuvent déclencher un renouvellement, tandis que `expire` impose un calcul frais. Les entrées persistantes sont limitées à 2 Mio, le stockage à 64 Mio et 8 192 entrées. Les résultats plus grands sont rendus sans persistance. Le rendu Flight est limité à 16 Mio.

La variante `private` peut lire `cookies()` et `headers()` et mémorise seulement dans la requête active, avec 128 entrées et 8 Mio au maximum. Elle ne peut pas être imbriquée dans un cache partagé. Draft Mode contourne aussi la persistance. Une portée publique interdit l'accès direct aux informations de requête.

Sans gestionnaire personnalisé, `remote` utilise le même cache Rust partagé entre les workers locaux. L'option `cacheHandlers` permet de choisir un stockage externe pour `default`, `remote` ou un nom supplémentaire tel que `analytics`, utilisé par `'use cache: analytics'`. Les modules JavaScript ou TypeScript sont compilés dans la partie privée du build ; ils exportent l'objet `get`, `set`, `refreshTags`, `getExpiration`, `updateTags` décrit par le [contrat Next](https://nextjs.org/docs/app/api-reference/config/next-config-js/cacheHandlers). `private` reste isolé par requête et ne peut pas être remplacé.

```js
export default {
  cacheComponents: true,
  cacheHandlers: { remote: './cache/redis-handler.ts' },
}
```

Le gestionnaire reçoit des `CacheEntry` contenant un flux d'octets, les tags, l'horodatage et les durées `stale`, `revalidate`, `expire`. `refreshTags` est appelé avant la première lecture de chaque requête, et les tags implicites `_N_T_` sont transmis à `get` et `getExpiration`. Les invalidations sont envoyées à tous les gestionnaires avant la réponse de l'action ou du handler. Une entrée périmée peut se renouveler en arrière-plan ; son expiration dure impose un calcul frais. Un échec de lecture ou d'écriture du stockage laisse le producteur répondre. Un échec d'invalidation reste une erreur, pour ne pas annoncer une mutation correctement actualisée quand elle ne l'est pas.

L'adaptateur limite les valeurs stockées à 2 Mio, les lectures de flux et appels de stockage à cinq secondes, et la déduplication locale à 64 productions simultanées. Le gestionnaire applicatif reste responsable de la capacité de son stockage, de la synchronisation entre instances et des courses d'invalidation distribuées. Ses données sont opaques : les octets PRNext ne sont pas interchangeables avec un cache de valeurs Next. Les résultats React et les données hors rendu utilisent des clés distinctes. Draft Mode contourne ces gestionnaires.

Les dépendances externes ne sont pas masquées par un cache HTML natif : les pages complètes concernées sont rendues à chaque requête et réutilisent leurs fonctions mises en cache. Leurs enveloppes PPR sont recalculées depuis les gestionnaires pour vérifier l'état partagé. Un cache natif parent ne persiste pas une valeur issue d'un gestionnaire externe. Les projets sans gestionnaire conservent leurs chemins natifs habituels. Le [`cacheHandler` singulier](incremental-cache.md), destiné au cache incrémental historique et aux pages complètes, possède un contrat distinct également pris en charge.

Les méthodes utilisant `this`, les instances de classes applicatives, les mutations de variables capturées et les flèches capturant un `arguments` extérieur sont refusés. Une fonction async ordinaire conserve ses arguments, même sans paramètres déclarés. Les artefacts et le protocole de cache restent propres à PRNext. La suite `tests/cache-handlers.test.mjs` vérifie le partage de données et de composants React entre deux serveurs, les invalidations de tags et de chemins, les modules livrés sans leurs sources et le redémarrage.

Références : [`use cache`](https://nextjs.org/docs/app/api-reference/directives/use-cache), [`cacheLife`](https://nextjs.org/docs/app/api-reference/functions/cache-life), [`cacheTag`](https://nextjs.org/docs/app/api-reference/functions/cache-tag).

Le rendu partiel produit au build une vraie enveloppe HTML, les données de continuation de `react-dom/static.prerender` et un arbre Flight statique. Les accès à `cookies()`, `headers()`, `searchParams`, `useSearchParams()`, `connection()`, aux fonctions `private` et aux fetchs non persistants délimitent les parties dépendant de la requête. Placer ces composants sous `<Suspense fallback={…}>` permet d'envoyer immédiatement l'enveloppe et les fallbacks ; `react-dom/server.resume` complète ensuite les parties manquantes. Les métadonnées dynamiques disposent aussi d'une frontière Suspense dans le layout racine. Si elles sont la seule partie dynamique d'une page, le build demande de les mettre en cache ou d'ajouter un marqueur `await connection()` sous Suspense, comme Next. Les composants client s'hydratent avec l'arbre Flight fusionné : les données statiques correspondent exactement au HTML du build, tandis que les parties privées viennent de la requête courante.

Ces artefacts partiels ne sont jamais enregistrés comme pages HTML complètes. Les réponses finales sont privées et non stockables par un cache HTTP partagé. Les enveloppes utilisent le cache natif, les durées et les tags découverts pendant leur production. Une génération persistante empêche de réutiliser les artefacts du build après une invalidation ; celle-ci peut aussi renouveler des enveloppes non concernées, par prudence. Les entrées dépassant la limite persistante de 2 Mio sont recalculées sans stockage. Le cache mémoire des artefacts de build est limité à 32 entrées et 8 Mio encodés. L'ensemble de la réponse reste limité à 16 Mio.

Les chemins complets de `generateStaticParams` sont préparés au build. Sans générateur, ou avec des paramètres seulement fournis par un layout parent, le build valide que la lecture des paramètres encore inconnus est sous Suspense et conserve une enveloppe générique réutilisable. Les paramètres parents connus sélectionnent des variantes distinctes : une enveloppe `locale=fr` ne sert pas `locale=en`. La première visite d'une URL inconnue envoie cette enveloppe avant de produire sa continuation concrète. Les clés de composants React sont adaptées aux paramètres réels dans le Flight final ; la reprise HTML conserve les clés attendues par la continuation opaque de React, sans modifier cette continuation ni remplacer du texte dans le protocole. Les paramètres aliasés des slots parallèles, templates et hooks de segments sont également couverts pour les chargements sans état de navigation conservé. Les continuations concrètes utilisent le cache natif entre requêtes et redémarrages. Lorsqu'elles deviennent entièrement statiques, les visites suivantes réutilisent leur Flight sans réexécuter l'arbre RSC. Les routes dont tous les paramètres sont générés mais qui autorisent d'autres valeurs, ainsi que les routes sans partie suspendue au build, peuvent encore créer leur enveloppe à la première visite. Les paramètres optionnels et catch-all suivent la même validation. Chaque `generateStaticParams` doit produire au moins un résultat avec Cache Components.

Les réécritures peuvent partager une enveloppe générique ; leur continuation concrète garde une identité distincte associant chemin destination et chemin visible ; `usePathname` reste cohérent entre HTML et hydratation. Les navigations et `router.refresh()` ordinaires reprennent aussi le PPR, avec paramètres et cookies de la requête courante et conservation de l'état client lorsque les clés React le permettent. Un accès non caché hors Suspense provoque une erreur de build et un diagnostic en développement. L'export littéral `instant = false` autorise explicitement une route bloquante ; un ancêtre `instant = true` conserve son exigence d'une enveloppe immédiate. La forme objet documentée `{ level: 'warning' }` déclenche des diagnostics de navigation en développement, sans échec du build. Ces probes rendent les sous-arbres sous chaque layout conservé : un fallback situé au-dessus de ce layout ne masque pas un blocage de navigation. Les erreurs apparaissent dans l'overlay de développement. Les options `unstable_disableValidation`, `unstable_disableDevValidation` et `unstable_disableBuildValidation` désactivent uniquement ces probes, jamais le contrôle obligatoire de l'enveloppe statique. `level: 'experimental-error'` active ces probes au build ; ce mode est expérimental. `unstable_samples` accepte jusqu'à 32 échantillons de cookies, en-têtes, paramètres et query, avec `null` pour une absence déclarée. Les déclarations de la page remplacent celles des layouts. Les valeurs ne sont utilisées que dans les probes de validation, jamais dans les enveloppes publiées ; une lecture non déclarée produit une erreur. `unstable_from` reste refusé explicitement, et les échantillons propres à plusieurs branches parallèles ne reproduisent pas encore tout le contrat Next. `instant` requiert Cache Components et ne peut pas être exporté par un Client Component. Voir le [contrat public instant](https://nextjs.org/docs/app/api-reference/file-conventions/route-segment-config/instant).

Draft Mode et Server Actions effectuent un rendu privé, avec lecture immédiate des mutations ; leurs réponses ne deviennent pas des enveloppes partagées. Une réponse avec nonce CSP effectue également un rendu par requête : la [documentation Next sur les nonces](https://nextjs.org/docs/app/guides/content-security-policy) impose cette contrainte, incompatible avec un nonce statique réutilisé. Les navigations de routes parallèles ou interceptées transportant l'état de branches conservées restent en SSR, afin de réautoriser chaque branche et ses métadonnées avec les credentials courants.

Le préchargement PRNext charge les segments statiques de l'enveloppe, sans exécuter les parties privées ou les fetchs non cachés. En production avec Cache Components, `Link` les précharge à l'approche du viewport et au survol ; `prefetch={false}` désactive ce comportement. `router.prefetch()` emploie le même chemin. Plusieurs URL d'une enveloppe générique partagent un arbre décodé identifié par son contenu ; le serveur ne renvoie pas le Flight déjà détenu. Les entrées de navigation expirent après 30 secondes et sont limitées à huit ; le cache des arbres partagés est limité à huit entrées et 2 Mio encodés, chaque réponse de préchargement à 768 Kio. Ce sont des plafonds d'octets encodés, pas une estimation exacte du tas React. La navigation effectue une nouvelle requête authentifiée, vérifie que l'identité de l'enveloppe et la destination sont toujours valides, puis affiche son UI statique pendant l'arrivée des parties dynamiques. Les actions et refresh invalident le préchargement. Les routes parallèles ou interceptées, Draft Mode et les réponses nécessitant un nonce ne préchargent pas d'enveloppe. Le cache réutilise un arbre de segments par enveloppe, sans découpage réseau indépendant de chaque layout entre routes différentes.

Pour les réponses partielles, le calcul de l'arbre serveur est encore parcouru afin de retrouver les parties dynamiques ; `'use cache'` évite de répéter les producteurs coûteux. Le protocole privé de Next n'est pas interchangeable avec celui de PRNext. Les contrats de diagnostic, les paramètres inconnus, `instant = false` et le comportement de build du niveau `warning` ont également été comparés à un build réel de Next 16.3.5. Références : [routes dynamiques](https://nextjs.org/docs/app/api-reference/file-conventions/dynamic-routes), [generateStaticParams](https://nextjs.org/docs/app/api-reference/functions/generate-static-params), [données bloquant le prérendu](https://nextjs.org/docs/messages/blocking-prerender-dynamic), [métadonnées bloquantes](https://nextjs.org/docs/messages/blocking-prerender-metadata-runtime).

La reprise parcourt aussi les `Map` et `Set` contenant des promesses de données de requête dans les props client. Les dates, tableaux typés et références partagées statiques sont conservés. Les valeurs des Map à clés primitives sont retrouvées par clé même si leur ordre change ; les clés objets et les éléments de Set sont associés par position. Une collection dont la structure dépend de la requête doit donc être construite entièrement dans la partie dynamique sous Suspense. Le délai maximal de 25 secondes couvre aussi la préparation du modèle, pour qu'une promesse non résolue ne bloque pas indéfiniment le pré-rendu.

Validation : enveloppe reçue avant un composant retardé, conservation des données statiques entre HTML et Flight, isolation des cookies y compris dans les collections Map/Set, hydratation interactive, paramètres de recherche, métadonnées dynamiques, fetch différé, `connection`, cache privé, expiration, tags, paramètres partiellement générés isolés par parent, enveloppe générique partagée entre URL, slots avec noms de paramètres distincts, templates, préchargement sans données privées et contrôle d'autorisation après changement de cookie, chemins non générés, réécritures, navigation/refresh, actions, nonce CSP, Draft Mode et redémarrage du serveur. Deux instances avec un gestionnaire externe vérifient aussi qu'une invalidation de tag actualise l'enveloppe PPR. API React utilisées : [`prerender`](https://react.dev/reference/react-dom/static/prerender), [`resume`](https://react.dev/reference/react-dom/server/resume).

Les probes `instant` prennent aussi en compte les pages de slots nommés, sous leur layout conservé. Un niveau `experimental-error` présent uniquement dans un slot active les probes de build ; les branches `warning` ne sont pas promues en erreurs de build. La fusion PPR conserve l’identité des promesses partagées et les cycles passant par une promesse. Les positions des grandes collections vivantes sont indexées une seule fois par fusion, au lieu de réallouer un tableau pour chaque trou dynamique. Les limites décrites plus haut sur les collections à structure variable et les échantillons par branche restent applicables.
